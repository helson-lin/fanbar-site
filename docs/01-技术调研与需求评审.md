# GEO Checker — 技术调研与需求评审

> 版本 v0.2 · 2026-10-28 · 状态：待评审（v0.2 新增第 3 节竞品分析）

## 1. 背景与目标

**GEO（Generative Engine Optimization）**：让网站内容更容易被 ChatGPT、Claude、Perplexity、Google AI Overviews、豆包、Kimi 等生成式引擎 **抓取 → 理解 → 引用**。

**产品目标**：用户输入一个 URL，几十秒内得到：

1. 一份 GEO 基础设施体检清单（每项：通过 / 警告 / 失败 / 不适用）
2. 一个总分与等级（A–F）
3. 可执行的诊断结论：问题按优先级排序，每条附「为什么重要 + 怎么修 + 示例代码」

**非目标（MVP 不做）**：AI 引擎中的实际排名/引用监测、全站深度爬取、内容质量的主观打分、关键词研究。

## 2. 关键调研结论（影响产品设计）

| # | 结论 | 对产品的影响 |
|---|------|-------------|
| 1 | GEO **没有官方标准**，各家 AI 厂商公开的只有爬虫 UA 和 robots 规则 | 文案要克制，不承诺"做完就能被 AI 引用"；分数定位为"基础设施完备度" |
| 2 | **llms.txt**（llmstxt.org，2024-09 提出）是社区提案；主流厂商未确认在检索时使用，Google 明确表示不使用 | 检测它，但**权重偏低**，并在说明中如实标注 |
| 3 | 多数 AI 爬虫（GPTBot、ClaudeBot、PerplexityBot 等）**不执行 JavaScript** | "原始 HTML 是否包含正文"是**最高权重**检查项之一，纯 CSR 站点是 GEO 头号问题 |
| 4 | Cloudflare 自 2025-07 起对新站点**默认拦截 AI 爬虫**；很多 WAF 也会拦 | 不能只看 robots.txt，要**用 AI 爬虫 UA 实际请求**，对比浏览器 UA 的响应 |
| 5 | AI 厂商普遍区分三类 bot：训练（GPTBot / ClaudeBot / Google-Extended）、搜索索引（OAI-SearchBot / Claude-SearchBot / PerplexityBot）、用户实时抓取（ChatGPT-User / Claude-User / Perplexity-User） | 分组展示；**屏蔽训练 bot 但放行搜索 bot** 是合理策略，不应判为失败 |
| 6 | JSON-LD（schema.org）是搜索引擎与 AI 理解实体最通用的结构化格式 | 按页面类型校验必填/推荐属性，而不是只看"有没有" |

> ⚠️ 第 2、4、5 条的细节（各家 UA 名单、厂商对 llms.txt 的态度）变化较快，开发前需再核实一次官方文档，并把 UA 名单做成可配置数据而非硬编码。

### 3.2 头号竞品实测：geo-optimizer-skill × getfanbar.com

工具得分 **78/100（Good）**，与人工复核对比如下：

| 维度 | 工具表现 | 评价 |
|------|---------|------|
| 覆盖面 | robots（27 个 AI 爬虫）、llms.txt、JSON-LD、meta、内容、CDN 实测访问、无 JS 可读性、Prompt 注入、信任度、RAG 分块等 19 类 | 很全，我们规划的 A–D 类它基本都有 |
| **漏报** | 没有识别 robots.txt 中的 `Content-Signal: ai-input=no`。这条声明不允许 AI 用内容生成回答或引用，和 GEO 目标直接冲突，是本站最严重的问题 | **关键缺陷**：只解析 Allow/Disallow，不理解新的内容使用声明 |
| 误报 / 低价值建议 | 推荐 `/ai/summary.json`、`/.well-known/ai.txt`、WebMCP 等非公认标准；把产品核心词 "fan control" 判为关键词堆砌；建议开源工具补地址和电话 | 建议里混有无依据的项，用户难以区分轻重 |
| 稳定性 | 目标站偶发超时时会重试，能完成审计（耗时 26s，超出其 10s 预算） | 可用 |
| 输出 | 终端报告 + JSON 等 8 种格式 + 网页报告链接 | 完善 |

### 3.3 结论：差异化方向

基础的"检查 llms.txt / sitemap / JSON-LD + 打分"已经有免费、开源、带网页版的成熟方案，**照原规划直接做没有差异**。可选差异点：

1. **准确优先，只给有依据的建议**：每条建议注明依据（官方文档 / 规范 / 社区提案），非标准项明确标注为"可选 / 证据不足"，不计入总分。
2. **识别"自相矛盾"的配置**：例如 `Content-Signal: ai-input=no`、搜索类 bot 被禁、noindex、WAF 拦截。这类问题直接导致 GEO 失效，应**置顶**，并触发评分上限规则（见第 5 节）。
3. **中文市场**：中文界面与诊断文案、国内 AI 爬虫（字节、百度、DeepSeek、Kimi、元宝等，UA 待核实）、国内常见建站与 CDN 环境。目前没有看到面向中文的同类体检工具（[GEOrank](https://github.com/cloudapp-dev/awesome-open-geo) 是中文的品牌监测工作台，定位不同）。
4. **面向非技术用户的诊断**：讲清楚"为什么重要 + 怎么修 + 可粘贴的代码"，按建站平台（Vercel、WordPress、Shopify 等）给出具体修复步骤。

### 3.4 自研还是基于竞品二次开发

| 方案 | 优点 | 缺点 |
|------|------|------|
| A. 自研 TS 检测引擎（原规划） | 规则完全可控，便于做"准确优先"；可部署在 Cloudflare 边缘 | 开发量大，覆盖面要追上竞品需要时间 |
| B. 以 geo-optimizer-skill（MIT）为引擎，外包一层中文网页版 | 上线快，覆盖面立即可用 | 后端改为 Python；继承它的漏报和误报，需要大量过滤和改写；上游变化快，难以维护；与 geoready.dev 同质化 |
| C. 自研引擎，参考竞品规则清单，复用 ai.robots.txt 与 llms-txt 规范（**推荐**） | 兼顾差异化和开发速度；规则只纳入有依据的项 | 仍需自研，但范围可控 |

## 4. 检测项设计

严重度：🔴 Critical（直接导致 AI 看不到内容） / 🟠 Warning（影响理解或引用质量） / 🔵 Info（加分项）

### A. 可访问性与爬虫准入（权重 30%）

| ID | 检测项 | 判定逻辑 | 严重度 |
|----|-------|---------|-------|
| A1 | HTTPS 与可达性 | 最终状态 200、重定向链 ≤ 3 跳、TTFB | 🔴 |
| A2 | robots.txt 存在且可解析 | `/robots.txt` 返回 200 + 可解析；404 视为全部允许（警告） | 🟠 |
| A3 | AI 爬虫 robots 规则 | 按 UA 列表逐个计算对目标 URL 的 allow/disallow，按"训练 / 搜索 / 用户抓取"分组 | 🔴（搜索类被禁） |
| A4 | AI UA 实测访问 | 用 GPTBot、ClaudeBot、PerplexityBot 等 UA 实际请求，对比浏览器 UA 的状态码与正文长度，识别 WAF/CDN 拦截（403、挑战页） | 🔴 |
| A5 | 页面级指令 | `<meta name="robots">`、`X-Robots-Tag` 中的 noindex / nosnippet / max-snippet | 🟠 |
| A6 | 内容使用声明 | 解析 robots.txt 中的 `Content-Signal`（search / ai-input / ai-train）；`ai-input=no` 或 `search=no` 与 GEO 目标冲突，`ai-train=no` 仅提示 | 🔴（ai-input=no） |

### B. 可发现性（权重 20%）

| ID | 检测项 | 判定逻辑 | 严重度 |
|----|-------|---------|-------|
| B1 | sitemap 存在 | robots.txt 中 `Sitemap:` 声明 → `/sitemap.xml` → `/sitemap_index.xml` 依次查找 | 🟠 |
| B2 | sitemap 合法性 | XML 可解析；urlset / sitemapindex 结构正确；单文件 ≤ 50,000 URL、≤ 50MB；支持 .gz | 🟠 |
| B3 | sitemap 质量 | `lastmod` 覆盖率与新鲜度；URL 与站点同域；抽样 N 个 URL 检查是否 200；目标 URL 是否在 sitemap 中 | 🔵 |
| B4 | llms.txt 存在 | `/llms.txt` 返回 200 且为文本（非 HTML 软 404） | 🔵 |
| B5 | llms.txt 格式 | 按规范：必须有 H1；建议有 `>` 摘要；H2 分节下的 `- [名称](url): 描述` 链接列表；抽样链接可访问 | 🔵 |
| B6 | llms-full.txt | 存在即加分 | 🔵 |

### C. 结构化数据（权重 25%）

| ID | 检测项 | 判定逻辑 | 严重度 |
|----|-------|---------|-------|
| C1 | JSON-LD 存在且可解析 | 提取所有 `<script type="application/ld+json">`，JSON 语法错误单独报出 | 🟠 |
| C2 | schema.org 类型识别 | 展开 `@graph`，列出所有 `@type` | 🔵 |
| C3 | 站点级实体 | 首页应有 `Organization`（含 name、url、logo、sameAs）和 `WebSite` | 🟠 |
| C4 | 页面级实体属性完整性 | 按类型校验必填/推荐属性：Article（headline、author、datePublished、dateModified）、Product（name、offers）、FAQPage、BreadcrumbList 等 | 🟠 |
| C5 | 与页面一致性 | JSON-LD 中的 name/headline 与 `<title>`/H1 是否大体一致 | 🔵 |
| C6 | 其他格式 | 检测 Microdata / RDFa，仅提示 | 🔵 |

### D. 内容可提取性与语义化（权重 25%）

| ID | 检测项 | 判定逻辑 | 严重度 |
|----|-------|---------|-------|
| D1 | 无 JS 可读性 | 原始 HTML 提取正文字数 vs 渲染后字数；原始 < 渲染的 30% 判失败 | 🔴 |
| D2 | 基础 meta | title（长度）、meta description、canonical、`<html lang>` | 🟠 |
| D3 | 标题层级 | 恰好 1 个 H1；H2–H6 不跳级 | 🟠 |
| D4 | 语义化标签 | `<main>` / `<article>` / `<nav>` / `<header>` / `<footer>` 使用情况 | 🔵 |
| D5 | Open Graph / Twitter Card | og:title、og:description、og:image | 🔵 |
| D6 | 图片 alt 覆盖率 | 有 alt 的图片占比 | 🔵 |
| D7 | 时效信号 | 可见日期或 dateModified | 🔵 |

### E. 可信度信号（P2，后续版本）
作者信息、About/Contact 页、`sameAs` 外链、外部引用等 E-E-A-T 信号。

## 5. 评分与诊断结论

**评分**：每项 0–1 分 × 项内权重 → 分类得分 × 分类权重 → 总分 0–100。
- 存在任一 🔴 失败时，总分上限 59（等级不高于 D），避免"其他都好但 AI 根本进不来"的误导性高分。
- 等级：A ≥ 90 / B ≥ 75 / C ≥ 60 / D ≥ 40 / F < 40。

**诊断结论生成**（两层）：
1. **规则引擎（P0）**：每个检测项自带结论模板（问题描述、影响、修复步骤、代码示例）。结果确定、可测、零成本。
2. **LLM 总结（P1，可选）**：把结构化结果交给 LLM 生成一段面向人的总结和"先做哪 3 件事"。只做总结与排序，不做判定，避免幻觉影响结论。

**输出**：Web 报告页（可分享链接）+ JSON API；P1 增加 PDF/Markdown 导出、llms.txt 与 JSON-LD 生成器（根据检测结果给出可直接粘贴的模板）。

## 6. 技术方案

### 6.1 架构

```
[前端 Web]  ──POST /api/scan──▶  [API 层]  ──▶  [检测引擎 core]
                                     │                 ├─ fetcher（安全抓取）
                                     │                 ├─ checks/*（每项一个模块）
                                     │                 └─ scorer + reporter
                                     ├─▶ [缓存/结果存储]（同 URL 10–30 分钟内复用）
                                     └─▶ [无头浏览器]（仅 D1 渲染对比用）
```

**核心原则**：检测引擎做成**与运行时无关的纯 TypeScript 包**，每个检测项是独立模块（输入：抓取上下文；输出：`{id, status, score, evidence, advice}`）。好处：易单测、可复用做 CLI / CI 插件 / 浏览器扩展。

### 6.2 部署方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A. Cloudflare Workers + Browser Rendering + KV/D1**（推荐） | 全球边缘、免运维、成本低；Workers 的 fetch 默认无法访问内网，SSRF 风险天然较低；Browser Rendering 可做 D1 渲染对比 | 出口 IP 是 Cloudflare 的，部分站点对其策略与真实 AI 爬虫不同（A4 结果需说明）；CPU 时间限制需注意大 sitemap 的流式解析 |
| B. Next.js（Node）+ Playwright 自托管 | 生态熟、调试方便、无运行时限制 | 需要自己做 SSRF 防护和浏览器池运维，成本较高 |

### 6.3 技术选型（TS 全栈）

- 前端：Next.js 或 Astro + Tailwind（报告页需 SSR 以便分享与被收录——GEO 工具自己也要符合 GEO）
- HTML 解析：Workers 用 `HTMLRewriter` / `linkedom`；Node 用 `cheerio`
- robots 解析：`robots-parser`（需验证 UA 分组与通配符匹配符合 RFC 9309）
- XML：`fast-xml-parser`，大文件流式处理
- 校验：`zod` 定义结果 schema，前后端共享类型
- 测试：`vitest` + 一组本地 fixture 站点（覆盖各种好/坏情况）

### 6.4 非功能需求（必须项）

| 类别 | 要求 |
|------|------|
| **SSRF 防护** | 只允许 http/https；解析 DNS 后拒绝内网/回环/链路本地/元数据地址（169.254.169.254）；**每一跳重定向都重新校验**；防 DNS rebinding |
| 资源限制 | 单请求超时 10s；整体扫描 ≤ 60s；HTML ≤ 5MB；sitemap ≤ 50MB 且流式；抽样链接 ≤ 20 个；并发受控 |
| 防滥用 | 按 IP 与按目标域名双重限流；匿名用户加 Turnstile 人机验证 |
| 对目标站点礼貌 | 自有 UA 标识（如 `GEOCheckerBot/1.0 (+https://<域名>/bot)`）；模拟 AI UA 的请求次数最少化 |
| 缓存 | 同一 URL 结果缓存，用户可手动"重新检测" |
| 性能目标 | P50 扫描完成 < 15s；前端分阶段流式展示进度（SSE） |

## 8. 风险

| 风险 | 应对 |
|------|------|
| GEO 规则变化快，检测项过时 | UA 名单、权重、规则做成配置；报告页标注"规则版本 + 更新日期" |
| A4 实测结果因出口 IP 不同而失真 | 报告中说明"模拟请求，可能与真实爬虫不同"；可选多出口 |
| 被拿来做扫描器/DDoS 跳板 | 限流 + 人机验证 + 单次请求数上限 + 域名级冷却 |
| 用户对"分数"过度解读 | 文案强调这是基础设施完备度，不等于 AI 引用率 |

## 9. 待确认问题

0. **自研还是二次开发**（见 3.4，优先确定）：是否采用推荐的方案 C（自研 TS 引擎 + 复用开源数据）？差异化方向（3.3）以哪几条为主？
1. **部署平台**：是否倾向 Cloudflare（6.2 方案 A）？还是已有其他云/服务器？
2. **检测范围**：MVP 只检测用户输入的单个页面 + 站点根文件（robots/sitemap/llms.txt），还是需要抽样多个页面？
3. **目标用户与语言**：面向国内还是海外？是否需要覆盖国内 AI 爬虫（如字节 Bytespider 等）和中文界面？
4. **账号体系**：MVP 是否需要登录、历史记录？
5. **LLM 总结**：是否在 MVP 就要？用哪家模型、成本预算？
6. **商业化**：免费工具引流，还是有付费档（API、批量、监控）？这会影响限流与架构设计。
